# 박영우 디자인 가이드 · Design Guide

> 모든 작업(이 포트폴리오, 렛츠 시리즈 서비스, AI 에이전트 작업)의 공통 기준. 2026-11-05 · 근거: 본인 인터뷰(INTERVIEW §14) + 세션 분석 4건(Claude·Grok·Gemini·Codex)
> 표기: [C] Claude · [Gr] Grok · [Gm] Gemini · [Cx] Codex

## 0. 한 문장
> **"모든 요소에는 이유가 있다."** 사용자가 보는 모든 표현은 실제 데이터와 행동의 결과여야 하고, 같은 의미는 어디서나 같은 규칙으로 작동하며, 그 결과는 모든 화면에서 흔들림 없이, 군더더기 없이, 재미있게 보여야 한다.

## 1. 가장 먼저 지키는 두 가지 (본인 답변)
1. **모든 환경의 반응형** — PC·태블릿·모바일, 모든 사람의 모든 환경에 최적화. 오래 걸리고 까다로워도 목표.
2. **사용성 중심** — 실제 사용자 입장에서 직접 써 보며 불편과 개선점을 찾는다.

> 그리고 AI 시대의 차별점: **요소 하나하나의 의도를 설명할 수 있을 것.** 균일한 품질을 끝까지 유지할 것.

## 2. 10가지 원칙

각 원칙은 **원칙 → 왜 → Do / Don't → 근거(실제 발언)** 순서입니다.

### 01. 흔들리지 않는 화면 (Stability)
- **왜:** 화면이 튀거나 겹치면 사용자는 내용보다 불안을 먼저 느낀다.
- **Do:** 겹침·잘림·튐 제로. 타이핑·스크롤·호버 중에도 레이아웃 고정. 좌우 여백은 대칭.
- **Don't:** 호버 시 버튼 이동, 뱃지 다닥다닥, 플로팅 버튼 겹침, 상단 테두리 잘림.
- **근거:** "모든 컨텐츠는 말풍선 안에서 좌우측 여백이 동일하게 안정된 상태로" · "블럭 겹치지 않고, 선 꼬이지 않고" · CCTV에서도 "안정적으로 보던 영상을 지속적으로" [C]

### 02. 하나의 의미, 하나의 규칙 (Consistency)
- **왜:** 같은 것은 같게 보여야 사용자가 배우지 않아도 쓴다.
- **Do:** 같은 개념 = 같은 아이콘·버튼 규격·용어·컴포넌트. 타이틀 크기와 아이콘 비율 통일. 헤더와 바디 폭 정렬.
- **Don't:** 같은 아이콘을 다른 의미로 사용, 같은 아이콘을 나란히 두 번, 모듈끼리 생김새가 겹쳐 구분이 안 됨.
- **근거:** "섹션 타이틀을 '2026년 9월' 텍스트와 통일한 크기로… 아이콘도 같은 비율로" [C] · 배지는 "얇은 캡슐 유지", 카드 높이 통일 [Gr] · 같은 개념엔 같은 댓글 모델 [Cx]

### 03. 한 건이 아니라 전체를 고친다 (Systemic Fix)
- **왜:** 같은 문제가 다른 화면에서 다시 나오면 고친 게 아니다.
- **Do:** 문제 발견 → 같은 유형 전수조사 → 케이스별 수정 → 재발 방지 규칙화.
- **Don't:** 지적받은 한 곳만 땜질.
- **근거:** "이러한 현상을 겪고있는 모든 UI를 스크린샷으로 검토해서" · "모든 브라우저 특성과 홈앱과 브라우저 등을 구분해서 케이스별로 모두" [C][Cx]

### 04. 원하는 정보만, 한 번만 (Reduction)
- **왜:** 정보가 많을수록 중요한 것이 묻힌다.
- **Do:** 같은 정보는 가장 알맞은 위치에 한 번. 출처·안내문은 (i) 아이콘으로 접기. 이미 시각 단서(퍼스널 컬러 등)가 있으면 텍스트 중복 표기 생략. 비슷한 기능은 하나의 버튼으로 통합.
- **Don't:** "달력을 좌우로 밀어…" 같은 장황한 안내, 의미 없는 섹션, 같은 기능 버튼 두 개.
- **근거:** "사람들이 원하는 정보만 보여줘" [C] · "UI를 지금보다 10분의 1로 간소화해서, 버튼은 버튼처럼, 내용은 내용처럼" · "'박영우 : 예당호'가 아니라 '예당호'로만" [Gm] · "비개발자가 보기에 어렵지 않고 복잡하지 않게" [C]

### 05. 표현은 데이터와 정확히 일치한다 (Truthful UI)
- **왜:** 화면이 실제 상태와 다르면, 예뻐도 거짓말이다.
- **Do:** 배지·상태·숫자는 실제 운영 상태와 일치. 불확실한 데이터는 숨김. 숫자는 사람의 언어로(직선거리 대신 내비 시간, "13만원대", "초3·고2"). 진행 상황은 `1/73`, 진행률 바로.
- **Don't:** 운영 중인데 '동계휴장' 배지, 썸네일 빈칸, 엉뚱한 후기 노출, 근거 없는 수치.
- **근거:** "썸네일 없는 기사는 목록에서 제외… 운영품질이 너무 떨어져 보여" [Gm] · '동계휴장' 배지 사례 [Cx] · "데이터 품질이 떨어지기 시작하면 전체가 의미가 없어집니다" [C]

### 06. 진짜처럼, 비율 그대로 (Visual Realism)
- **왜:** 어설프게 흉내 낸 그래픽은 서비스 전체를 싸 보이게 한다.
- **Do:** 실사·고해상도 에셋, 필요하면 진짜 스프라이트·렌더. 이미지 원본 비율 유지. 회전축·조명·각도까지 레퍼런스와 일치.
- **Don't:** CSS·SVG로 대충 만든 게임 그래픽, 늘어난 버튼 이미지, 블러리한 효과, 회전 시 흔들리는 머리 위치.
- **근거:** "버튼 이미지 늘려서 쓰지 말고" · "스프라이트 이미지를 생성하라고" · 360° 룩북 "머리 위치가 항상 고정" [Gm] · 아크릴 버튼 투명감·볼륨·조명, 파티클 크기 1.5배·개수 2배 [Gr]

### 07. 한국어를 위한 타이포그래피 (Korean Typography)
- **왜:** 한국어는 단어가 쪼개지는 순간 읽기 어려워진다.
- **Do:** Pretendard 단일 서체, weight 대비로 위계. `word-break: keep-all`. 헤드라인의 쉼표·마침표 제거. 브랜드명 띄어쓰기 통일('렛츠 캠핑'). 강조할 것과 힘 뺄 것 구분.
- **Don't:** 서체 혼용(Noto 등), 모바일에서 다단 그리드로 인한 어색한 줄바꿈.
- **근거:** "Pretendard만" [Gr] · "콤마나 마침표는 모두 제거" · "'렛츠 캠핑'으로 띄어쓰기" [Gm] · "강조할 것과 힘을 뺄 것을 구분" [C]

### 08. 320px부터, 실제 기기에서 (Real-device Responsive)
- **왜:** 사용자는 시뮬레이터가 아니라 각자의 휴대폰으로 본다.
- **Do:** 320px를 마지노선으로 검증. PC·태블릿·모바일별 단 수와 박스 처리를 명세(예: PC 1단+4단 라운드 박스 / 태블릿 2단 / 모바일 1단 꽉 차게). iOS 사파리 홈 앱·키보드·100dvh·안전 영역, 삼성인터넷·웨일 대응.
- **Don't:** 375px 기준 타협, 작은 화면에서 다단 유지.
- **근거:** "모바일 320px 가로폭의 사파리, 삼성인터넷에서도" [Gm] · 반응형 단 수 직접 명세 [C] · 폴드 포함 [Cx]

### 09. 만지고 싶은 화면 (Delight & Tactility)
- **왜:** 글만 많은 화면은 읽히지 않는다. 손이 가야 머문다.
- **Do:** 이미지·그래프·카드 등 섹션 성격에 맞는 다양한 UI. 촉각형 인터랙션(스크래치, 스와이프, 투표 후 결과 그래프). 모션은 이해를 돕는 데 사용(동선이 보이는 애니메이션). 요즘 미감: 가는 막대 + 큰 숫자, 컨셉이 형태로 드러나게.
- **Don't:** 게시판형 단조로운 목록, 두껍고 올드한 그래프, 색만 바꾼 '리디자인'.
- **근거:** "글만 많아서 읽고 싶지가 않아. 재미가 없어" · "'만지는 뉴스'라는 컨셉이 이례적이고 굉장히 괜찮아" · "막대그래프가 두꺼우니까 미련해 보이고 올드해 보여" · "온도계면 좀 더 온도 개념의 디자인이" · "색보정한거야? 형태는 그대로네?" [C]

### 10. 빠른 것도 디자인이다 (Performance as Design)
- **왜:** 아무리 화려해도 멈추면 실패한 디자인이다.
- **Do:** 체감 속도 우선, 무거운 동작엔 상태 피드백. 비용까지 고려한 설계(무료 범위 우선).
- **Don't:** 버튼 한 번에 브라우저 먹통, 같은 로딩 문구 수십 번 반복.
- **근거:** "도로보기 버튼을 누르면 브라우저가 순간 먹통… 가볍고 빠르게" · "1/73 이런 식으로 전체 프로세스를 한눈에" [Gm] · Firebase 읽기 요금까지 챙김 [Gr]

### 취향 메모 (Taste)
- 차분한 바탕 + 채도 높은 포인트 컬러(블랙·화이트·라임 / 브랜드 네이비 + 오렌지), 둥근 모서리와 보이는 그림자, 촘촘한 레이아웃, 중간 굵기 타이포 [C·Taste]
- 넓고 와이드한 레이아웃, 히어로 이미지, 스크롤·마우스 인터랙션, 서사적 소개 [Cx·인터뷰]
- 서비스마다 테마는 다르게 — 포트폴리오(all)는 흰 라이트 기본, 렛츠 캘린더 리디자인은 나이키 피트니스 레퍼런스

## 3. 협업 프로토콜 (AI·동료와 일할 때)

작업 전에 **네 가지를 먼저 고정**합니다. [Cx]

1. **불변 규칙**: 이 문서의 10원칙 + 프로젝트별 금지사항
2. **시각 기준**: 기준 시안 / 레퍼런스 / 현재 화면 캡처
3. **실제 데이터 상태**: 빈 데이터·긴 텍스트·이미지 없음 등 엣지 케이스
4. **완료 검증표**: 아래 항목을 채워야 '완료'

| 완료 보고에 반드시 포함 | 내용 |
|---|---|
| 원인 | 왜 생겼는가 (추측 아님) |
| 적용 범위 | 같은 유형 전수 수정 목록 |
| 전후 화면 | 실제 배포 화면 스크린샷 |
| 기기별 검증 | 320px · iOS 사파리(홈 앱) · 삼성인터넷 · 웨일 · 데스크톱 · 라이트/다크 |
| 회귀 방지 | 추가한 규칙·테스트 |
| 남은 리스크 | 못 한 것, 할 수 없는 것은 솔직하게 |

> 할 수 없으면 바로 말한다. "안 되겠으면 안 되겠다고 얘기를 하세요." [C]
